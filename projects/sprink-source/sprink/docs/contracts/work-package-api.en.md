# Work-package API contract (storage lane, draft)

Source: design revision 3 in [#1](https://github.com/my-name-is-yu/InnovationCup/issues/1). Implementation: #3 / #7. This contract is intentionally small; engine adapters may translate their richer models into these boundary records.

- Base: `/api/work-packages`. Existing `Authorization: Bearer <application token>` applies. No new identity/tenant system; project/package ownership is checked for every referenced asset. All IDs are strings.
- `POST /` creates `{projectId, title, intent}` with optional `sourceDrawing`, `baselinePlan`, `scope`, `siteFacts`, `detailing`, `changeRequest`. Both intents can start as drafts independently. No prewritten reroute, earlier package, or change is needed for preparation.
- `GET /?projectId=...` lists packages; `GET /:id` returns the saved snapshot and derived freshness. `PATCH /:id` accepts `{expectedRevision, patch}` for the above inputs (project/intent immutable). User changes increment `inputRevision`. Derived writes do not.
- `POST /:id/assets`: multipart `file`; PDF, PNG or JPEG, max 20 MiB. Immutable registered bytes. `GET /:id/assets/:assetId` requires the owning package. An uploaded asset is not yet a confirmed drawing or site fact.
- `GET /:id/candidates`, `/outputs`, `/requests`, `/artifacts` return saved values plus freshness. `POST /:id/selection` with `{expectedRevision, planId}` explicitly adopts a current retained candidate (or baseline) and increments the revision. Selection is neither approval nor an as-built observation.
- `POST /:id/answers` with `{expectedRevision, requestId, value, unavailableReason}` records a durable answer. It does not silently confirm site facts; use a subsequent input patch for factual confirmation.
- `POST /:id/runs` accepts `{expectedRevision, goal}` (`prepare_from_drawing`, `adapt_to_site`, `export_selected_package`). Duplicate start at the same input returns the active run. `GET /:id/runs/latest` polls progress; `POST /:id/runs/:runId/cancel` cancels only that run. Human waits end a run; rerun manually with saved inputs.
- `GET /:id/artifacts/:artifactId/download` serves only current, registered, package-owned output bytes. Rendering belongs to #13.

`inputRevision: number` + a single deployed `configVersion: string` determine freshness. Snapshots expose `freshness` derived at read time; no readiness state machine is persisted. Edits interrupt current runs; cancellation and restart reject late writes. Server startup changes persisted `running` to `interrupted`; it never replays tools.

Confirmed baseline geometry/source drawing is frozen in that package. A new source revision is a new package; staged baseline edits are allowed before confirmation. Alternative plans remain in candidate outputs/selectedPlan, separate from baseline. Explicit site facts include `observed` versus `installed`; candidates cannot mutate either.

## Integration seams

- Core contract: `packages/core/src/work-package.ts` (runtime schemas and inferred types).
- Server: independent `apps/server/src/work-packages/` router, store and service. Shares the existing Store database. Parent `api.ts` mounts one router after auth middleware. Existing task/rule APIs are unchanged.
- Runner is an injected `WorkPackageRunner` port, with immutable input snapshot, abort signal, progress and revision-checked output publishing. No runner is configured by default: start returns **503 runner_unavailable**. Unit/API tests inject a clearly synthetic controlled runner.
- Domain payloads are boundary contracts, not replacement engine implementations. Adapters for #6, #9, #10, #2 and #13 remain explicit integration work. No Pi, JEV, route search, materials math or PDF/CSV renderer is implemented here.
- Assets use an independent package-owned table; legacy task asset IDs cannot be reused. Export adapter first registers generated bytes through the service, then publishes artifact metadata bound to the same run and output IDs.

Errors use `{error, code}`: 400 invalid input, 404 absent/not-owned, 409 revision/conflict/stale output, 413 size, 415 unsupported media, 503 runner unavailable. Reload snapshot after 409; do not silently retry with a newer revision.

Runnable synthetic request/response examples for both scenarios will be in `docs/contracts/examples/`. They prove transport/persistence behavior, not constructability or live engine integration.

## Parallel-lane DTO adapter notes

Inspected the other lanes read-only on September 26; these are integration notes, not a claim that those in-progress packages are installed or wired here.

| Lane | Adapter work at integration |
|---|---|
| `packages/workflow` (`WorkflowRunner`, `DomainPort`, `RunStore`) | Inject one `WorkPackageRunner` into the server service. Project the saved package into `WorkSnapshot`, including current output refs and actual input gaps. Route `DomainPort.commit` through `context.publish`; translate stale-write errors to `false`. Connect the outer abort signal to workflow cancellation. The current workflow runner allocates its own run ID and run store: unify this with the server's run ID/latest summary rather than adding a second durable run lifecycle. Persist `request_input` questions via `publish({requests})` before returning `waiting_input`; otherwise the API cannot answer them. |
| `packages/fabrication` (`FabricationInput` / `FabricationOutput`) | Explicitly map drawing ports/entities to nodes, fabrication pieces, fitting ports and detailing/access inputs. Normalize declared units to millimetres for the plan boundary, preserving the engine's metric units in quantities. Map cuts' sourceSegmentIds to sourceEntityIds and ordered operations to assembly steps. Preserve source/product/datum/procedure information before declaring #3/#10/#13 integrated; this minimal summary DTO is not a lossless replacement for FabricationOutput. |
| `packages/planning` (`GenerateInput` / `CandidateSet`) | Assemble measured obstacle/work envelope and product constraints from confirmed inputs. No defaults for missing dimensions. Convert each retained plan to PackagePlan with proposed confirmation, preserve rejection/search information, and convert comparison metrics without replacing null by zero. Publish the entire finite candidate set; selection remains exclusively the user API. |
| Browser workbench | Translate local `expectedInputRevision` to HTTP `expectedRevision`, and local command variants to PATCH, selection, answers or runs. There is no generic `/commands` endpoint. After 409 reload the snapshot and present the conflict. |
| #13 exports | Use the same run context to register bytes and publish PackageArtifact metadata with resultId/planId and matching inputRevision/configVersion. Source asset GET never serves artifact bytes. Rendering is outside this PR. |

The current plan boundary is deliberately limited to explicit ports/connections and a right-handed, Z-up millimetre frame. It does not claim the node/datums, fabrication splits, catalog evidence, detailed evaluation coverage or planning boxes have already been reconciled across independently developed lane models. Do not silently drop them in a production adapter. The richer DTO union/storage extension should be agreed once those lane PRs are available.

`QuantityValue` carries `basis: confirmed_inputs | proposed_inputs | unknown`; null values require a reason and `unknown` basis. A known value derived from a proposed plan remains `proposed_inputs`. Numeric values, including runner output, must be finite. The package's source approval remains independent of all these states.

## Running and reproducing

```sh
cd sprink
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
# Focused persistence/HTTP suite:
pnpm exec vitest run apps/server/test/work-packages.test.ts
```

The configured server starts with no production runner. `SPRINK_CONFIG_VERSION` supplies the single deployed version; the default `work-package-contract-v1` identifies this unintegrated contract slice. Bump the configured value when any output-affecting engine/catalog/rule/template changes.

To attach an implementation in the server composition root, create `new WorkPackageService(new WorkPackageStore(fieldService.store.db), configVersion, runner)` once and pass it as `createApp(fieldService, {token, workPackages})`. On shutdown call `workPackages.close()` before closing SQLite. No other lane source needs to be copied into this worktree.

Use the two `.create.json` examples as POST bodies; their matching `.response.json` documents normalize server-generated IDs and timestamps. Start with a draft, upload a source file, then PATCH its returned asset ID into `sourceDrawing` together with the staged/confirmed model. An approved source reference and a confirmed baseline are immutable. New source revisions start a new package; there is no implicit baseline migration.

Outputs examples are synthetic boundary payloads for `PackageRunContext.publish`, not public write APIs or real computed quantities. Public clients read them from `/outputs` or `/candidates`. HTTP users cannot write outputs, run summaries, selectedPlan, project ownership or configVersion through PATCH.

## Verification boundary

Validated: 16 work-package HTTP/SQLite tests plus all 86 existing tests (102 total), and core/server/web TypeScript checks. The focused suite checks both published create/response examples, JSON output fixtures through the publish port, concurrent expected-revision writes, bearer auth, decoded PNG upload and package/project isolation, unknown values, explicit candidate adoption, partial results/questions, stale artifacts, duplicate start, cancellation/input-edit races, failed runners, actual SQLite close/reopen, and config changes.

The controlled runner never invokes Pi, JEV, a geometry/materials engine or an export renderer. Its artifact bytes are explicitly synthetic; no real PDF/CSV output, source-backed construction quantities, browser workbench acceptance, live service connection or field constructability has been verified in this storage/API PR. These remain downstream integration/release checks.
